# Development roadmap and governance

## Build in evidence-bearing increments

Keep the working native architecture and preserve inherited behavior unless a selected contract changes it. Release reports describe what exists; the master describes where the product is going. A complete data catalog, imported actors, screenshots and model checks are useful inputs, each with limited scope.

| Milestone | Product purpose | Evidence |
| --- | --- | --- |
| v0.1–v0.2 | Web movement/world/objective exploration | Historical prototype/source |
| v0.3 | Unreal migration, movement, geometry, restricted observation | Pinned engine, native builds, saved assets and independent clients |
| v0.4–v0.5 | Growth, navigation, coherent UI/inventory/trade | Legal actions, native input and transaction/privacy checks |
| v0.6 | Bounded economy, banks, production and public Charter | Conserved sources/sinks and earned zero-kill route |
| v0.7 | Tactical combat, acquisition and four routes | B70–B77 reports, native route/control/ownership evidence |
| v0.8 | Mixed actions, eleven bindings, traits, river/field interactions, full catalogs | B80–B86 reports and measured limits |
| v0.9 | Full geography, functional environment, living population and full matches | B90–B94 gates below |
| Later | Refine fun, learnability, balance, operating readiness | Repeated observed matches and measured risks |

## Active full-map sequence

B90 → B91 → B92 → B93 → B94 is a strict dependency chain. B90 establishes deterministic terrain, roads, rivers, settlement structure and native access. B91 adds real environment interactions, interior completion and synchronized collision/sight/nav mutations. B92 adds bounded full-profile economy, roster, routines, security and legal AI progression. B93 converges the four earned routes in the capital. B94 establishes full-duration, restricted-client, stress and human evidence.

Use the exact [stage plan](../v09/09_IMPLEMENTATION_STAGES.md) and acceptance IDs. A structural preview is useful for review but does not certify interactive cities or a playable full match. Do not move past a failed required gate by relabeling markers as gameplay.

## Definition of done

A feature needs one authority path, native behavior, meaningful rejection/boundary checks, synchronized data/assets and reviewable evidence. Its report states profile, source revision, engine/build, command, setup and limits. Label grants/teleports/clock edits as fixtures. Normal progression demonstrations must earn the resources they use.

Keep templates blank and use separate working ledgers. Record Not implemented, Failed, Not run and Deferred distinctly. A deferred gate remains a release limitation; it is not a pass. Preserve source archives and prior evidence. Store machine-specific output in ignored Artifacts and portable selected evidence under the release directory.

## Change discipline

Update semantic source/generator, rebuild compiled payloads/assets, validate consistency and revise the relevant contract together. Unknown behavior-affecting IDs or fields fail import. New profiles start fresh matches; no silent mixing of timers, coordinates, sources or inventories.

Commit coherent increments with stage IDs and actual validation. Do not edit a frozen historical report to make later changes appear to have existed earlier. Keep current continuation and root indexes useful to the next developer.

## Risks and later decisions

Track raw-stat dominance, control-chain frustration, inventory bypasses, hidden-information leaks, dominant routes, stock/cash exhaustion, empty travel, recovery downtime and server cost. Proposed subclasses, spell variants, control diminishing returns, deeper factions, physical caravans, squads and public hosting need explicit decisions and evidence. None is implied by full-map scope.
